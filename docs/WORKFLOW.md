# Workflow

## 목적
이 문서는 task를 진행할 때의 작업 순서와 상태 관리 규칙입니다.

## 문서 우선순위
1. 사용자 직접 요청
2. 현재 진행 중인 작업 요청
3. `docs/WORKFLOW.md`
4. `docs/PLANS.md`
5. 나머지 프로젝트 문서

## 작업 흐름
작업을 처음 구현할 때 아래 순서로 진행합니다.

1. 관련 요청과 선행 산출물을 확인합니다.
2. `docs/PLANS.md`에서 현재 단계 상태를 `진행중`으로 갱신합니다.
3. `docs/ARCHITECTURE.md`와 `docs/STYLEGUIDE.md`를 확인합니다.
4. 관련 코드를 읽습니다. 관련 코드가 없으면 건너뜁니다.
5. 생성/변경 후보 파일과 범위를 정리합니다.
6. 구현을 진행합니다.
7. `docs/TESTING.md` 기준으로 확인합니다.
8. 구현 후 필요한 상태 문서만 실제 결과 기준으로 갱신합니다.
9. 필요한 수동 확인 항목을 사용자에게 안내합니다.
10. 확인이 끝난 단계는 `docs/PLANS.md`에서 `완료`로 갱신합니다.

## 문서 기록 규칙
- `docs/PLANS.md`의 작업 상태는 task 진행에 필요한 경우 갱신합니다.
- 디버깅 로그, 상세 작업 로그, 최근 작업 로그는 사용자가 요청할 때만 남깁니다.
- 매 구현마다 로그를 자동 추가하지 않습니다.
- 코드 변경 사실은 최종 응답에서 요약하고, 문서에는 필요한 결정 사항이나 명시 요청된 기록만 남깁니다.
- 구현 중 애매한 판단이 있으면 작업을 먼저 완료한 뒤 최종 응답에서 사용자에게 확인합니다.

## 진행 제약
- 현재 단계에 명시된 것만 구현합니다.
- 범위 밖 기능이 필요하면 이유와 변경 범위를 먼저 정리합니다.
- 비밀값, API 키, 인증 토큰은 읽거나 기록하지 않습니다.
- 구현과 문서 갱신은 필요한 범위 안에서만 함께 반영합니다.
